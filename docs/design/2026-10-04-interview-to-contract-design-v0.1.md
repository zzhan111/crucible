## 1. 定位

### 1.1 一句话
**让任何领域的专家通过一场"会追问、会对数据"的对话，把自己的判断变成一份可执行、可溯源、经过校准的 Crucible 评分契约。**

流水线：**访谈（反弹） → 契约 → 评分**。产品不预设领域：入口是一个空白会话，用户自己定义场景，用户本人就是专家。

### 1.2 目标用户
| 用户 | 典型例子（仅示意，均不是试点） | 他要什么 |
|---|---|---|
| **领域专家（主用户）** | 便利店店长判断 SKU 是否符合顾客预期；医药采购判断 ERP 采购单是否合理；招聘负责人判断简历；分析师判断竞品情报表 | 不写代码、不学 YAML，把"我一看就知道好坏"的经验变成可复用的标准；看到标准和自己的判断是否一致 |
| **AI 应用构建者（次用户）** | 给某个生成 agent 找一个"懂行"的评测器 | 通过 MCP 拿到一份已校准契约，对 agent 产物打分 / 在生成前自检 |

### 1.3 非目标（v1 不做）
- 不做通用聊天助手；每个会话必须产出契约草稿（或明确放弃）。
- 不内置任何行业模板或默认领域；模板只能来自用户自己发布过的契约（v2 再说）。
- 不做多专家共识/投票（v1 单专家；第二评审者只用于校准上限，见 §3.6）。
- 不做 BI / 报表工具；数据只用于"问得准"和"对账"，不做可视化分析产品。
- 不让 LLM 生成可执行代码谓词（`code_predicate`）——现有沙箱降级到 `node:vm`，隔离弱。
- 不负责生成被评工件本身（那是 P3"规则前移到生成期"的事）。
- v1 不做实时语音（§6.2 留接口）。

## 2. 核心概念

### 2.1 Session = Scenario
- 界面形态与现有 AI 聊天产品一致：左侧会话列表，一个会话 = 一个场景 = 一份契约（含版本历史）。
- 会话第一步由用户定义场景，系统只问"填空题"，不给领域预设：

| 场景槽位 | 说明 | 例 |
|---|---|---|
| `artifact` 被评对象 | 要打分的"东西"是什么 | 一张采购单 / 一份门店 SKU 清单 / 一份简历 |
| `unit` 评价单元 | 行级（每个 SKU/每行采购）还是整份 | 行级 |
| `purpose` 决策用途 | 分数被谁用来做什么决定 | 采购员下单前自检 |
| `stakes` 犯错代价 | 放过坏的 vs 错杀好的，哪个更贵 | 缺货 > 积压 |
| `data` 可用数据 | 能附上的本地数据 | SKU 主数据、POS 销售、库存 |
| `outcome` 外部结果信号 | 事后能验证好坏的真实数据（可空） | 30 天动销率、退货率 |

- **v1 只支持 `table` 族（行=节点）**【待定】：专家+本地数据的场景大多是表格（SKU、采购行、候选人），且现有谓词/rubric 大多是 table 族。`sequence` / `brief` 放到 v2。

### 2.2 访谈状态机

```
 ┌─────────┐   ┌────────┐   ┌──────────────┐   ┌────────────┐   ┌──────────┐   ┌────────┐   ┌────────┐
 │S0 定义场景│──▶│S1 读数据│──▶│S2 访谈(反弹) │──▶│S3 结构化草稿│──▶│S4 样本排序│──▶│S5 校准  │──▶│S6 发布 │
 └─────────┘   └────────┘   └──────▲───────┘   └─────┬──────┘   └────┬─────┘   └───┬────┘   └───┬────┘
                    ▲ 用户随时补数据   │  覆盖度不足/冲突未决 │  专家点评产生新规则 │ τ 低/残差大  │ 线上结果数据回流
                    └─────────────────┴────────────────────┴───────────────────┴──────────────┘ (回到 S2，带针对性问题)
```

| 状态 | 进入条件 | 做什么 | 退出条件（门槛均为【假设】，需试用后调） |
|---|---|---|---|
| S0 定义场景 | 新建会话 | 填 §2.1 槽位 | `artifact`、`unit`、`purpose` 已填 |
| S1 读数据 | 有附件（无附件可跳过） | 数据画像 + 生成针对性问题（§4） | 画像完成，问题池非空 |
| S2 访谈（反弹） | — | 提问、追问、质疑、要例子；实时抽取（§3.1–3.5） | 覆盖度达标（§3.4）或专家主动"先出草稿" |
| S3 结构化草稿 | — | 确定性编译出契约草稿；在真实数据上试跑规则，看通过率是否离谱 | 专家逐条确认/驳回；`disputed` 项为 0 或明确挂起 |
| S4 样本排序 | 草稿可编译 | 生成样本批次（含埋雷）→ 专家分档/排序/点评 | 有效排序样本数 ≥ 目标（默认 20，【假设】） |
| S5 校准 | — | 门控检出率 + Kendall τ（含置信区间）+ 残差分析 | 专家看过一致度报告并接受；否则带残差问题回 S2 |
| S6 发布 | 校准完成 | 冻结版本，生成 Crucible YAML + 溯源包，经 MCP 暴露 | — |

关键设计：**状态机允许回退**，而且每次回退都携带"为什么回来"的具体问题（数据冲突、样本点评、排序残差、线上结果偏差），而不是重新从头访谈。

### 2.3 契约对象模型（ContractSpec）

两层结构：
1. **ContractSpec（源）**：中间层的工作对象，含溯源、状态、例子、冲突，存于会话数据库。
2. **Crucible YAML（编译产物）**：由**确定性代码**（不是 LLM）从 ContractSpec 编译而来，现有字段保持兼容，扩展字段放在新的顶层键下。

> 兼容性事实：现有 `ContractSchema` 是普通 `z.object`，默认会**静默剥离**未知顶层键——所以扩展键不会让旧 loader 报错，但也**不会生效**。这正是 §5 必须先修引擎的原因。

#### 2.3.1 四层内容（对应你提出的四层）

| 层 | Crucible 现有落点 | 扩展后 |
|---|---|---|
| ① 硬规则 | `fields`（未校验）+ `hard_constraints`（每条只扣 0.15） | 规则原语 + `enforcement: gate\|penalty\|lint`；`fields` 真正校验【依赖 P1】 |
| ② 证据要求 + 来源分级 | 无（`source_trust` 由工件自报） | `evidence_requirements` + `source_tiers`，trust 由来源等级查表推导，不再信自报值 |
| ③ 评分维度（权重 + 好/坏例） | `rubric[]: dim/weight/mode`（确定性维度权重被忽略） | 增加定义、可观察信号、锚点、好/坏例、judge 规格；权重生效【依赖 P1】 |
| ④ 专家排序的黄金样本 | 全局 8 个工件 + 单人排序；`GoldenArtifact.region` 写死三个地名 | 每契约独立黄金集，20–30+，含埋雷样本、分档、点评、holdout 划分【依赖 P1/P2】 |

#### 2.3.2 字段级 schema（YAML 示意；示例内容为虚构的采购场景，仅示意）

```yaml
# ── Crucible 兼容核心（引擎读取）──
metadata:
  contract_id: "c_7f3a"            # 新增：契约身份（现缓存 key 只用 version，跨契约会撞）
  version: 0.3
  status: draft                    # draft | calibrating | published
  scenario_id: "s_12"
artifact_family: table
blend: { deterministic: 0.6, judge: 0.4 }   # 新增，替代 augmented.ts 写死常量【依赖 P1】

fields:                            # 现有结构 + 扩展属性
  - name: order_qty
    type: integer
    required: true                 # 【依赖 P1】必须真校验
    unit: "盒"                      # 新增
    data_binding: "po_lines.qty"   # 新增：映射到用户数据列
    quote_refs: [q_031]            # 新增：溯源

hard_constraints:
  - id: qty_vs_30d_sales           # 现有：id + type
    type: declarative
    rule: "单次采购量不超过近 30 天销量的 2 倍"   # 人类可读原句（保留）
    primitive: ratio_threshold     # 新增：通用规则原语（见下）
    params: { numerator: order_qty, denominator: sales_30d, op: "<=", value: 2.0 }
    enforcement: gate              # 新增：gate=拒绝不打分 | penalty | lint【依赖 P1】
    exceptions: ["新品首单", "促销备货"]
    status: confirmed              # proposed | confirmed | disputed | retired
    data_check: { pass_rate: null, checked_at: null }  # 在用户真实数据上的试跑结果
    test_cases: { pass: [g_04], fail: [g_19] }
    quote_refs: [q_031, q_044]

evidence_requirements:             # 新增层②
  - id: ev_price_source
    applies_to: { field: unit_price }
    min_tier: T2
    max_age_days: 90
    quote_refs: [q_052]
source_tiers:                      # 新增：trust 由等级推导
  - { tier: T1, name: "本地交易数据（POS/ERP）", trust: 1.0 }
  - { tier: T2, name: "专家亲历 + 具体实例",      trust: 0.8 }
  - { tier: T3, name: "公开文档/行业报告",        trust: 0.6 }
  - { tier: T4, name: "LLM 常识（不可单独作证据）", trust: 0.0 }
  # trust 数值为【假设】，由专家在 S3 确认

rubric:                            # 现有 dim/weight/mode + 扩展
  - dim: substitution_risk
    weight: 0.30
    weight_source: elicited        # elicited | fitted | default
    mode: judge
    definition: "缺货时顾客是否有可接受的替代品"
    observables: ["同类目同功效 SKU 数", "替代品价差"]
    anchors: { 1: "...", 3: "...", 5: "..." }
    good_examples: [{ ref: g_02, why: "...", quote_refs: [q_060] }]
    bad_examples:  [{ ref: g_11, why: "...", quote_refs: [q_061] }]
    judge_spec:                    # 通用 judge【依赖 P2】
      inputs: [sku_name, category, alternatives]   # 字段白名单，防止重复计分
      output: { score: "1-5", rationale: str, evidence_quotes: "str[]" }
      samples: 3                   # 取中位数

calibration:                       # 现有 + 扩展
  frozen_golden_set: "golden/c_7f3a/v0.3.jsonl"
  metric: kendall_tau              # 需支持 τ-b（专家分档会产生并列）【依赖 P2】
  holdout_ratio: 0.3               # 【假设】
  outcome_signal: { metric: "sell_through_30d", available: false }

# ── 溯源（单独 sidecar 文件 provenance.json，不进引擎）──
# quotes:   { q_031: { session_id, turn_id, char_span, verbatim, ts, audio_ref? } }
# conflicts:{ cf_07: { claim_ref, query, result, status, resolution_quote } }
```

**规则原语库**（解决"compiler 用 `switch(c.id)` 硬编码、未知 id 被跳过"的问题）：中间层只允许产出能被通用编译的原语——`required`、`enum_in`、`range`、`regex`、`unique`、`ratio_threshold`、`cross_field`（字段间算术/比较）、`lookup_in_ref`（值必须在用户参考表里）、`aggregate_threshold`（整份工件的占比/合计）、`freshness`。表达不了的规则降级为窄 judge 维度或标记 `needs_impl`，**`needs_impl` 项存在时契约不能发布**（fail-loud）。原语清单为初稿【待定】。

## 3. 中间层设计（重点）

中间层 = 从"专家说的话 + 用户数据"到 ContractSpec 的全部逻辑。由 5 个角色组成，**只有前 4 个用 LLM，编译与校准全部是确定性代码**：

| 角色 | 输入 → 输出 | LLM? |
|---|---|---|
| Interviewer（访谈者） | 缺口队列 → 下一个问题（含反弹） | 是 |
| Extractor（抽取器） | 新的专家发言 → 候选条目（带原话锚点） | 是，结构化输出（zod） |
| Reconciler（对账器） | 可检验断言 → 查询 → 结果 → 冲突 | 生成查询用 LLM，执行与判定确定性 |
| Sample Builder（样本构造） | 草稿契约 + 数据 → 样本批次（含埋雷） | 部分（变异算子确定性） |
| Compiler / Calibrator | ContractSpec → YAML；排序 → τ / 检出率 | 否 |

### 3.1 抽取
- 每轮专家发言后增量抽取，输出候选条目：`field | hard_rule | evidence_req | rubric_dim | example | claim | exception | weight_hint`。
- 每个候选带 `confidence` 与 `status=proposed`，出现在右侧契约预览里，专家一键 确认/改/驳回。
- 抽取器还负责把规则**落到原语**（如"别一次进太多货"→ `ratio_threshold` 的骨架，阈值留空 → 生成追问"多少算太多？"）。

### 3.2 溯源（硬约束，不是指标）
- **每个条目必须挂 ≥1 条专家原话**（`quote_refs`，含会话、轮次、字符区间、原文）。无原话的条目不能进入 `confirmed`。
- LLM 自己提出的建议（例如"要不要加一条有效期规则？"）标记为 `origin: ai_suggested`，只有专家在对话中明确认可后，以**认可那句话**为溯源。防止"AI 替专家说话"。
- 专家在侧栏直接改字段 → 记为 `origin: direct_edit` 的溯源事件。
- 校验：抽取器给出的 `verbatim` 必须是原文的精确子串（确定性检查），否则丢弃该锚点并重抽。

### 3.3 冲突检测
三类冲突，都转成追问进入缺口队列：
1. **专家 vs 数据**：可检验断言与数据不符（§4.3）。
2. **专家 vs 专家**：前后两条陈述矛盾（如前面说"临期品一律不进"，后面举例进了临期促销品）。
3. **专家 vs 自己的排序**：S4 排序与已确认规则/权重矛盾（如违反 gate 规则的样本被专家排在前面）。

冲突状态：`open → expert_revised | data_wrong | accepted_divergence（专家坚持，记录理由）`。发布前 `open` 必须为 0；`accepted_divergence` 保留在契约里供审计。

### 3.4 覆盖度 / 完备度：何时"访谈够了"
不用单一分数，用一张**检查清单**；所有门槛为【假设】，试用后调整：

| 检查项 | 判定 | 默认门槛 |
|---|---|---|
| 场景槽位 | `artifact/unit/purpose/stakes` 已填 | 全部 |
| 规则可执行 | 每条 hard_rule 有原语+阈值+作用范围+例外立场 | 全部 |
| 规则有测试 | 每条 gate 规则至少 1 个通过例 + 1 个违反例 | 全部 |
| 维度可操作 | 每个 rubric 维度有定义 + 可观察信号 + ≥1 好例 + ≥1 坏例 | 全部 |
| 权重已问 | 权重来自专家取舍回答，而非默认均分 | 全部 |
| 数据对账 | 可检验断言均已检验；`open` 冲突数 | 0 |
| **区分度** | 规则/确定性维度在真实数据上不是全过或全不过（审计教训：`cost_fit` 在 8 个黄金样本上全为 1.0，零区分度） | 无全过/全挂项，或专家确认这是预期 |
| 饱和 | 最近 N 轮专家回答没有产生新条目 | N=3 |
| 溯源 | 已确认条目的原话覆盖率 | 100%（硬性） |

清单在侧栏实时显示为"还差什么"，同时就是 Interviewer 的提问来源。专家可以随时"先出草稿"，未达标项在草稿上标黄。

### 3.5 反弹策略：LLM 何时追问 / 质疑
缺口队列按 **影响 × 不确定性** 排序：gate 规则 > 高权重维度 > 证据要求 > 低权重维度。触发器：

| 触发 | 识别方式 | 反弹动作 | 例 |
|---|---|---|---|
| 模糊词 | "合理/新鲜/太多/差不多" | 要可观察的定义或阈值 | "'太多'是超过几天的销量？" |
| 绝对化 | "从不/一定/所有" | 要反例、问例外 | "有没有你破例进过的情况？" |
| 无例子 | 规则/维度无实例 | 要一个真实的好例和坏例 | "举一个你见过最典型的坏采购单" |
| 数据冲突 | Reconciler 产出 | 摆数据，问解释 | "你说周末饮料卖得多一倍，过去 8 周数据是 1.2 倍，差在哪？" |
| 前后矛盾 | 专家 vs 专家冲突 | 让专家二选一或给适用条件 | — |
| 不可观察 | 标准无法从工件字段看出 | 问"在表里哪一列能看出来？" | — |
| 硬/软不明 | 规则未定 enforcement | "违反这条是直接不合格，还是扣分？" | — |
| 硬规则过多 | gate 规则在真实数据上拒掉很大比例 | 质疑是否该降为扣分 | — |
| 权重不明 | 两维度都"重要" | 取舍题："两者冲突时保哪个？" | — |

约束：
- **同一条目最多反弹 2 轮**【假设】，之后记为 `expert_asserted`（专家断言、未验证）并降低该项在校准中的先验，不纠缠。
- 不引导：问题必须开放式，禁止"是不是应该 X？"式暗示（prompt 约束 + 抽检）。
- 反弹语气是"请教 + 追问细节"，不是辩论；每轮最多一个反弹点。
- **投入档位**（专家选择，决定反弹深度与样本数；时长均为设计目标【假设】）：
  - 快速：只覆盖 gate 规则 + 前 3 个维度，10 个样本分档 → 产出"草稿契约"（不可发布）
  - 标准：完整清单，20 个样本 → 可发布
  - 深度：+ 证据要求细化、30+ 样本、holdout、隔日复排（重测信度）

### 3.6 样本、排序与校准（S4–S5）
- **样本来源**（优先级）：① 用户真实数据中的行/工件；② 对真实样本做**确定性变异**埋雷（把数量改成超阈值、删必填字段、换成低等级来源），已知埋了哪条规则；③ LLM 合成（只用于补数据中缺的类型，标记 `origin: synthetic`）。
- **样本粒度**：单个样本应能在约 1 分钟内被判断【假设】；整份工件太大时按行抽样。
- **埋雷样本**用于测 gate 的检出率（应被拒），**不参与 τ**（或按审计建议置底）；正常样本用于 τ。
- **低摩擦排序**：先拖进 好/中/差 三档，再在档内两两比较（只比较不确定的对）；每个样本可加一句点评。点评经 Extractor 抽取 → 新候选规则/例子 → 回 S2。
- **即时一致度反馈**：每完成一批，显示"契约排序 vs 你的排序"的 Kendall τ-b + bootstrap 置信区间 + 分歧最大的 3 对（"你把 A 放在 B 前，但契约给 B 更高分，主要差在 X 维度——哪里不对？"）。小样本时置信区间很宽（审计：n=8 时零假设下 τ 标准误约 0.29），界面必须如实展示，不报单点数字。
- **权重**：以专家取舍回答为准（`elicited`）；可用排序数据拟合（`fitted`），但**只在训练部分拟合、在 holdout 上报 τ**，并向 elicited 权重正则化——避免重蹈简历轨道"在同一 11 份黄金集上网格搜索 3000 个权重变体"的过拟合。
- **人类上限**：深度档提供"隔日复排"作为重测信度；有第二位专家时作为 human ceiling。
- **真实结果回流（发布后）**：有 `outcome_signal`（如动销）时，计算契约分与结果的秩相关，并与专家排序和结果的相关对比；显著背离的样本作为新冲突回到 S2。注意结果数据受混杂因素影响（促销、陈列、季节），只作参考信号，不自动改契约。

## 4. 数据接入与量化对账

### 4.1 接入
- 支持 CSV / xlsx（多 sheet）/ docx / pdf / md。表格进本地分析库（DuckDB），文档切块后用于证据检索。
- **本地优先**【待定】：原始数据留在本地；默认只把**数据画像与聚合查询结果**发给 LLM，不发原始行。可按会话开关"允许发送样例行"。

### 4.2 访谈前读数据（S1）
- 画像：列名/类型推断、缺失率、分位数、Top-K、异常值、时间范围、候选主键、表间可能的关联键。
- 生成针对性问题，例：
  - 发现 15% 的 SKU 近 90 天零销量 → "这些长期零动销的品为什么还在？是刻意保留的吗？"
  - 发现采购量分布长尾 → "这几笔超大单是什么情况，算正常吗？"
- 列与契约字段的映射（`data_binding`）由 LLM 提议、专家确认。

### 4.3 对账：断言 → 查询 → 判定
1. Extractor 把可检验的陈述转为结构化断言：`{metric, filter, groupby, comparator, value, tolerance}`。
2. Reconciler 生成 SQL（LLM），**只读执行**（DuckDB），结果与 SQL 一起存档。
3. 判定（确定性）：`consistent | conflict | uncheckable(缺数据/口径不明)`；容差默认值【假设】，在断言中显式记录。
4. `conflict` → 进缺口队列成为追问；`uncheckable` → 问专家是否能补数据或给口径。
5. 草稿规则在真实数据上**试跑**，得出通过率（`data_check`），用于区分度检查和"硬规则过多"反弹。

> 对账的目的不是证明专家错，而是把"经验"和"数据"的差异显性化。数据也可能错（口径、缺失、录入），所以 `data_wrong` 是合法的冲突结局。

## 6. 前端 MVP

### 6.1 v1（文本）范围
三栏布局：
- **左：会话列表**（一个会话一个场景，显示状态机阶段与契约版本）。
- **中：聊天**。附件拖入即进入 S1；系统消息里内嵌"数据冲突卡片"（显示断言、SQL 结果、三个按钮：我修正 / 数据有问题 / 坚持原判并说明）。
- **右：契约实时预览**，标签页：硬规则｜证据要求｜评分维度｜样本｜冲突｜完备度清单。
  - 每条目显示状态色（proposed / confirmed / disputed）、数据试跑通过率；点击即高亮对应原话。
  - 支持直接编辑（记为 `direct_edit` 溯源）。
- **样本排序界面**（S4，全屏模式）：卡片 → 拖入 好/中/差 → 档内两两比较 → 每卡可写点评；底部即时显示 τ-b + 置信区间 + 最大分歧对。
- **发布页**：版本 diff（复用现有 `ContractPatch` / Human Gate 审批语义）、导出 YAML + 溯源包、MCP 接入说明。

v1 明确不做：多人协作、移动端、模板市场、语音。

### 6.2 v2（语音）
- 语音只用于 S2 访谈；排序、确认仍在屏幕上（语音不适合逐条确认）。
- 流式中文 ASR + TTS；溯源锚点增加 `audio_ref`（时间戳），因为转写可能有误，专家可回放原声核对。
- 转写纠错是溯源可信的前提：确认条目前，引用的转写片段需专家可见可改。
- 轮次控制（打断、静音判定）与"每轮一个反弹点"的规则在语音下更重要。

## 7. 技术选型、里程碑、风险、开放问题

### 7.1 技术选型（建议）
| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | TypeScript（与 Crucible 同仓或同 monorepo） | 直接复用 zod schema、compiler、calibration |

| 存储 | SQLite（Crucible 已用 better-sqlite3）存会话、条目、溯源、版本 | 本地优先；平台化再换 Postgres |
| 数据 | DuckDB（CSV/xlsx/parquet）+ SheetJS；docx/pdf 解析 | 本地只读 SQL，适合对账 |
| 前端 | React / Next.js | 聊天 + 侧栏 + 拖拽排序的常见组合 |
| 对接 | 进程内 → MCP（现有 `src/mcp/`） | 见 §5.1 |
| 语音（v2） | 流式 ASR/TTS 服务【待定】 | — |

### 7.2 里程碑（工作量为粗估，未经验证）
| 里程碑 | 内容 | 验收（可观察，不预设数值） |

### 7.3 风险
| 风险 | 应对 |
|---|---|
| LLM 把话塞进专家嘴里（诱导、过度概括） | 原话精确子串校验；`ai_suggested` 必须经专家认可；问题开放式；抽检 |
| 专家疲劳 / 半途放弃 | 投入档位；侧栏显示"还差什么"；随时可出草稿；排序优先于长访谈 |
| 小样本校准噪声大 | 强制展示置信区间；holdout；不在评估集上调权重 |
| 硬规则过严导致误拒 | 真实数据试跑通过率 + "硬规则过多"反弹；默认新规则先 penalty，专家确认后再升 gate【待定】 |
| 合成/变异样本不真实，导致排序无意义 | 真实样本优先；合成样本标记并可单独统计 |
| 规则原语表达力不足 | 降级为窄 judge 维度；`needs_impl` 阻止发布；收集未覆盖规则驱动原语扩充 |
| 单专家偏见 | v1 接受；记录 `accepted_divergence`；结果数据回流作为外部校验 |
| 数据隐私 | 本地优先、默认只发画像/聚合；会话级开关 |
| 结果数据混杂（促销、季节） | 只作参考信号，不自动改契约 |
| 引擎依赖延期 | M0 是硬前置；M1/M2 可先基于 ContractSpec 开发，不依赖引擎 |
